# HU-00 · Preparar la base del proyecto en AWS y Azure DevOps

**Como** líder técnico del taller **quiero** tener listos los repos, los pipelines, las libraries, el acceso a AWS y la infraestructura base **para** que las HU-01 a HU-03 solo construyan y desplieguen el micro.

Convenciones del proyecto `workshop-peru`:

- `{proyecto}` = `transfers`. Repos: `pragma-ms-java-pragma-transfer` (micro), `pragma-iac-tf-pragma-transfer` (Terraform) y `pragma-azure-devops-tf-pipeline` (template corporativo de IaC).
- Las libraries se llaman igual que su repo.
- Un solo ambiente: **dev**. Las tareas corren en `us-east-1a`; el ALB interno usa además una subred en `us-east-1b` porque exige dos zonas. Los pipelines se disparan con push a `main`.
- Autenticación del API: **API key** (`x-api-key`) en API Gateway y header `X-Customer-Id` para identificar al cliente. Sin JWT.
- Persistencia en **DynamoDB** (on-demand). Cómputo en **ECS Fargate**.
- Los secretos viven en la library del micro y su pipeline los escribe en Secrets Manager; Terraform solo crea el secreto vacío.

**Acceso a AWS (cuenta `123456789012`, sin llaves en ningún lado):**

| Rol | Lo usa | Para qué |
| --- | --- | --- |
| `pragma-workshop-peru-devops-role-dev-deploy` | Service connection `aws-service-connection-dev` (OIDC) | Solo asume los dos roles de abajo |
| `pragma-workshop-peru-devops-role-iac` | Pipeline de IaC (`AWS_DEPLOY_ROLE` de su library) | Crear la infraestructura con Terraform |
| `pragma-workshop-peru-devops-role-app` | Pipeline del micro (`AWS_DEPLOY_ROLE` de su library) | ECR, escribir el secreto de las APIs y reiniciar servicios ECS |

La service connection y el rol van en las libraries (`AWS_SERVICE_CONNECTION` y `AWS_DEPLOY_ROLE`), nunca escritos en el YAML.

**Infraestructura base ya creada** (`us-east-1`). Terraform no la crea, solo la lee:

| Recurso | Nombre | Configuración |
| --- | --- | --- |
| ECR del micro | `pragma-transfers-dev-ecr-ms-transfers` | Escaneo al subir, tags mutables (`latest`), AES256, conserva 20 imágenes |
| ECR de mocks | `pragma-transfers-dev-ecr-mocks` | Igual que el del micro; guarda WireMock con los stubs |
| Bucket del state | `pragma-transfers-dev-workload-trf01-terraform-state` | Versionado, AES256, acceso público bloqueado y tags de `common_tags` |

El nombre del bucket lo arma el template: `{CLIENT}-{PROJECT}-{ENVIRONMENT}-{INFRASTRUCTURE}-{CODE_APP}-terraform-state`, con `pragma`, `transfers`, `dev`, `workload` y `trf01` de la library de IaC.

**Accesos de los participantes:** Contributor en `workshop-peru`, permiso de edición en las libraries, aprobador del environment `main` (HU-02) y acceso de lectura a la cuenta de AWS.

## Criterios de aceptación

```gherkin
Escenario: repositorios inicializados
  Dado el proyecto workshop-peru en Azure DevOps
  Entonces existe pragma-ms-java-pragma-transfer con el scaffold del micro, su Dockerfile, mocks/ y deployments/azure-pipelines.yml
  Y existe pragma-iac-tf-pragma-transfer con la estructura base de Terraform y su azure-pipelines.yaml
  Y existe pragma-azure-devops-tf-pipeline con el template corporativo de IaC
  Y los pipelines del micro y de IaC están registrados

Escenario: infraestructura base en AWS
  Entonces existen los ECR pragma-transfers-dev-ecr-ms-transfers y pragma-transfers-dev-ecr-mocks con escaneo al subir la imagen
  Y existe el bucket pragma-transfers-dev-workload-trf01-terraform-state con versionado, cifrado y acceso público bloqueado

Escenario: libraries inicializadas
  Entonces la library pragma-ms-java-pragma-transfer tiene AWS_DEPLOY_ROLE con el ARN de pragma-workshop-peru-devops-role-app
  Y la library pragma-iac-tf-pragma-transfer tiene AWS_DEPLOY_ROLE con el ARN de pragma-workshop-peru-devops-role-iac
  Y los secretos del micro están marcados como secretos

Escenario: acceso de los pipelines a AWS
  Entonces los pipelines entran con la service connection aws-service-connection-dev
  Y cada uno asume su rol (role-iac o role-app) con los permisos que necesita
  Y no hay llaves de AWS en el repo, en las libraries ni en los scripts

Escenario: ambientes de Azure DevOps
  Entonces existe el environment main con aprobación antes del apply de Terraform
  Y existe el environment dev para el despliegue del micro
```
