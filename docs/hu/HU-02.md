# HU-02 · Desplegar ms-transfers en dev con Terraform y Azure Pipelines

**Como** equipo de desarrollo **quiero** crear la infraestructura de `ms-transfers` con los módulos de referencia de Pragma y desplegar el micro con su pipeline **para** tener el micro corriendo en dev sin crear nada a mano.

Repo: `pragma-iac-tf-pragma-transfer`. Library: `pragma-iac-tf-pragma-transfer`. Ambiente: `dev`. Variables de Terraform en `environments/dev/terraform.tfvars`. El pipeline asume `pragma-workshop-peru-devops-role-iac`.

Diagrama: `docs/arquitectura-dev.drawio` (exportado en `docs/arquitectura-dev.png`). Estrategia: `docs/deployment-strategy.md`.

**Ya existe (HU-00), Terraform solo lo lee con `data`:**

| Recurso | Nombre |
| --- | --- |
| ECR del micro | `pragma-transfers-dev-ecr-ms-transfers` |
| ECR de mocks (WireMock + stubs) | `pragma-transfers-dev-ecr-mocks` |
| Bucket del state | `pragma-transfers-dev-workload-trf01-terraform-state` |

**Recursos que crea Terraform:**

- Red privada en dos zonas (`us-east-1a` y `us-east-1b`) con salida por NAT Gateway y VPC endpoints gateway para DynamoDB y S3.
- **NLB interno** en las subredes privadas, con target group tipo `ip` hacia el servicio `ms-transfers` en el puerto 8080. Dejar `deregistration_delay` en 30 s: con el valor por defecto (300 s) cada despliegue espera 5 minutos de drenaje.
- **API Gateway REST API** con VPC Link hacia el NLB:
  - Recurso `/{proxy+}` con método `ANY`, integración `HTTP_PROXY` a `http://<nlb>/{proxy}` y el mapeo `integration.request.path.proxy = method.request.path.proxy`. Así cualquier ruta del micro (también las de la HU-03) queda expuesta sin cambios.
  - **API key** (`x-api-key`) con usage plan (`api_throttle_rate_limit`, `api_throttle_burst_limit`). **Sin JWT.** El cliente se identifica con el header `X-Customer-Id`.
- Cluster ECS con capacidad Fargate y dos servicios con sus task definitions, ambos con la imagen `:latest` de su ECR:
  - `ms-transfers` (1 tarea).
  - `mocks` (1 tarea, WireMock con los stubs de `mocks/` del repo del micro), expuesto por **Service Connect** como `http://mocks:8080`.
  - La task definition del micro no necesita variables ni `secrets`: los valores llegan desde la library del micro al construir la imagen y las llaves se leen del secreto al arrancar.
- DynamoDB on-demand:
  - `transfers`: llave `transferId`; GSI `sourceAccountId-createdAt-index` (`sourceAccountId` + `createdAt`) y GSI `customerDay-createdAt-index` (`customerDay` + `createdAt`), los dos con proyección `ALL`.
  - `idempotency`: llave `idempotencyKey`, TTL en `expiresAt`.
  - `recipient-tokens` (HU-03): llave **`recipientToken`**, TTL en `expiresAt`.
- SNS `transfers-events` con suscripción a SQS `notifications` y su DLQ.
- Secreto vacío de las APIs en Secrets Manager con su llave KMS; el valor lo escribe el pipeline del micro.
- IAM:
  - Task role del micro: DynamoDB, `sns:Publish`, `secretsmanager:GetSecretValue` y `kms:Decrypt` sobre el secreto de las APIs.
  - `pragma-workshop-peru-devops-role-app` debe permitir `DescribeSecret` y `PutSecretValue` sobre el nombre real del secreto.
- Log groups y alarmas en CloudWatch.
- Outputs: `ecs_service` y `secret_apis_name` (más los que hagan falta para la library).

**Pipelines:**

- **IaC** (`azure-pipelines.yaml`): extiende el template corporativo de Terraform. Prerequisites (tags del bucket del state), CI (Checkov), Validation (validate y plan), Approval (environment `main`) y CD (apply).
- **Micro** (`deployments/azure-pipelines.yml`): Build (escribe los valores de la library en `application.yml` y construye las imágenes `:latest` del micro y de `mocks/`), Secrets DEV (llaves de la library al secreto `SECRET_APIS_NAME`) y Restart ECS DEV (`update-service --force-new-deployment` de mocks y del micro, con avance cada 15 s). Asume `pragma-workshop-peru-devops-role-app`.

**Después del primer apply: llenar la library del micro** (*Pipelines → Library → `pragma-ms-java-pragma-transfer`*):

| Variable | Valor |
| --- | --- |
| `ECS_CLUSTER` | nombre del cluster |
| `ECS_SERVICE` | output `ecs_service` |
| `ECS_MOCKS_SERVICE` | nombre del servicio de mocks |
| `SECRET_APIS_NAME` | output `secret_apis_name` |
| `DYNAMODB_ENABLED` | `true` |
| `DYNAMODB_TABLE_TRANSFERS` / `DYNAMODB_TABLE_IDEMPOTENCY` / `DYNAMODB_TABLE_RECIPIENT_TOKENS` | nombres reales de las tablas |
| `SNS_ENABLED` | `true` |
| `SNS_TOPIC_ARN` | ARN del tópico `transfers-events` |
| `CORE_BASE_URL` / `FRAUD_BASE_URL` / `DIRECTORY_BASE_URL` | `http://mocks:8080` |
| `CORE_API_KEY` / `FRAUD_API_KEY` / `DIRECTORY_API_KEY` | llaves de prueba, marcadas como secretas |

Luego correr de nuevo el pipeline del micro: escribe los secretos, construye la imagen con esos valores y reinicia las tareas.

**Probar el API** (`API_URL` = output `api_base_url`, `API_KEY` = valor de la API key):

```bash
API_KEY=$(aws apigateway get-api-key --api-key API_KEY_ID --include-value --query value --output text)
curl -i API_URL/actuator/health -H x-api-key:$API_KEY
```

Sin el header `x-api-key`, API Gateway responde 403 y la petición no llega al micro.

## Criterios de aceptación

```gherkin
Escenario: plan de la infraestructura
  Dado un push a main en pragma-iac-tf-pragma-transfer
  Cuando corre el pipeline de IaC
  Entonces usa el bucket del state pragma-transfers-dev-workload-trf01-terraform-state
  Y ejecuta Checkov, validate y plan asumiendo pragma-workshop-peru-devops-role-iac
  Y el plan solo contiene recursos declarados con módulos de referencia
  Y los dos ECR se leen con data sources, sin crearlos

Escenario: apply con aprobación
  Cuando el plan termina
  Entonces el apply espera la aprobación del environment main
  Y aplica el plan con environments/dev/terraform.tfvars

Escenario: library del micro completa
  Dado que el primer apply terminó
  Cuando reviso la library pragma-ms-java-pragma-transfer
  Entonces tiene ECS_CLUSTER, ECS_SERVICE, ECS_MOCKS_SERVICE, SECRET_APIS_NAME, los nombres de las tablas, SNS_TOPIC_ARN y las URLs de los mocks

Escenario: tablas con el esquema del micro
  Entonces la tabla transfers tiene los GSI sourceAccountId-createdAt-index y customerDay-createdAt-index en ACTIVE
  Y la tabla recipient-tokens tiene la llave recipientToken y TTL en expiresAt

Escenario: mocks en dev
  Cuando el pipeline del micro termina en main
  Entonces la imagen de mocks está en pragma-transfers-dev-ecr-mocks con el tag latest
  Y el micro alcanza los mocks en http://mocks:8080 por Service Connect

Escenario: llaves desde el secreto
  Dado que la library tiene CORE_API_KEY, FRAUD_API_KEY y DIRECTORY_API_KEY como secretos
  Cuando corre el pipeline del micro
  Entonces escribe esos valores en el secreto SECRET_APIS_NAME
  Y el micro los lee del secreto al arrancar con su task role
  Y los valores no aparecen en logs, en la imagen, en el repo ni en el state de Terraform

Escenario: despliegue del micro
  Cuando el pipeline del micro termina en main
  Entonces las tareas de mocks y del micro se reiniciaron con la imagen latest
  Y el servicio ms-transfers queda con 1 tarea sana en el target group

Escenario: API key
  Cuando envío una petición al API Gateway sin x-api-key
  Entonces recibo 403 de API Gateway y la petición no llega al micro

Escenario: rutas de API Gateway
  Cuando llamo GET /api/v1/accounts/191-0001234567/transfers con x-api-key válida y X-Customer-Id CUST-000123
  Entonces el micro recibe esa misma ruta y responde 200

Escenario: sin llaves de AWS
  Entonces el pipeline de IaC asume role-iac y el del micro role-app desde la service connection
  Y ningún script ni library contiene llaves de AWS

Escenario: red privada
  Entonces ninguna tarea ni el balanceador tienen IP pública
  Y el balanceador es interno y solo recibe tráfico del VPC Link
```
